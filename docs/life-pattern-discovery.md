# 共有モデル・行動パターン発見との互換性

対応するサーバー変更: [switch_bot_python PR #9](https://github.com/shunsuke-tanaka-creator/switch_bot_python/pull/9)。方式の選択はサーバーの`research_architecture`で行い、iPhoneでLSTMの学習やクラスタ生成は行わない。

## 表示上の区別

拠点（Place）は生活上の場所、行動パターン（Behavior）は個人固有の作業・行動のまとまりを指す。新方式では一つの三階層エンコーダから両者と現在・日次5尺度を推定する。24活動分類は別の推定器として同時実行せず、過去の活動回答を事後説明・比較用として保持する。

アプリの案内を「拠点・行動パターン」へ整えた。旧サーバーでも意味が破綻しないよう、推定方式と機能はサーバー設定に従う旨を明示する。候補の名前は本人による解釈であり、未確認候補を自動で「研究」「食事」などへ確定しない。

## 変更しない保存・通信契約

- `placeCheck`と`taskCheck`をそのまま使う。`taskCheck`は新方式のBehaviorの確認であり、独立した第二のTaskモデルを意味しない。
- 確認イベントの軸は`place`/`task`、IDは既存形式のまま。新しい`behaviorCheck`やIDの一括置換は導入しない。
- 質問ID、発行対象の5分区間、回答・訂正、命名・統合、永続outboxと冪等再送を維持する。
- 24カテゴリの回答や既存のローカル保存ファイルを削除しない。アップデート時に旧回答を書き換えない。
- 新サーバーの`behavior`と互換フィールド`task`は同じ内容。Web画面は`architecture`/`version`/`model_id`を伴うサーバー側の結果を扱い、旧推定を新モデルの結果とみなさない。

同一拠点で別作業、別拠点で同じ作業をそれぞれ独立に確認する。場所・行動が分からない場合は「わからない」を使い、推測による回答を要求しない。

## 移行時の注意

既存サーバーへの接続は維持できる。新方式を使う場合はサーバーPRを先に検証し、`research_architecture=discovery`を明示する。既定のlegacy経路は変更しない。チェックポイントは新規学習し、旧モデルと保存先を分ける。アプリ更新だけでは方式は切り替わらない。

新方式の候補生成はバッチ再学習時であり、iPhone表示のたびにクラスタを増やすものではない。未学習・古い観測・支持不足では候補または不明となる。新しい行動IDに対応する歩数基準・介入は未検証のため、サーバー新方式では運動・休憩の自動提案判定を停止する。設定スイッチをONにしても、サーバーの検証条件を迂回して提案しない。

## 検証

既存のSimulator検証でビルド・共通契約を確認する。実機の通知時刻、オフライン回答の再送、既存データを保持した更新、実ログでの意味分離・精度は別途確認が必要である。推論アルゴリズムのテストはPython側に置き、iOSのビルド成功をモデル精度の証明としない。
